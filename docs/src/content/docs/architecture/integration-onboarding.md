Third-party integrations in x1agent are wired in through a **dynamic registration flow**, not by pasting credentials into a config file. The operator clicks a button in the admin UI, gets bounced to the provider, confirms, and lands back on a working integration. Private keys, client secrets, and webhook secrets never transit any x1agent.com infrastructure — they flow directly from the provider to the operator's own api server, into the operator's own secret store.

This is the architectural rule. It applies to every integration the install can talk to.

## Why

A typical SaaS platform's GitHub integration starts with: "Register an App on github.com, copy these six values into a `.env` file, restart the server." For an operator self-installing on their own cluster, that means handling a multi-line PEM private key by hand, getting it onto a server they may not have shell access to, and hoping the secret store accepts the format. Most operators get this wrong on the first try.

The platforms that ship cleanly — Linear, Notion, Figma, Vercel — never make their customers handle credentials. They use one of four patterns, and we use the same set in the same priority order.

## Preferred patterns, in order

### 1. First-party manifest / app-creation flow

When the provider publishes a manifest flow (GitHub App Manifest, Slack App Manifest), use it. The operator clicks a button. We render a pre-filled form with the App's name, URLs, permissions, and webhook events. The browser submits to the provider. The operator confirms on the provider's side. The provider creates the App on the operator's own account and redirects back to our api with a single-use `code`. Our api server-side calls the provider's exchange endpoint and gets the App's full credentials in one response. We persist them into the operator's secret store.

The operator pastes nothing. The credentials never leave the operator's own infrastructure.

This is the right pattern for **GitHub Apps**. See ticket X1A-81 for the in-progress implementation of the admin-UI button.

### 2. Per-user OAuth with offline access

When the integration is scoped to an individual user's data — their Google Drive files, their Notion pages, their Linear issues — use per-user OAuth. The user signs in via the provider's OAuth consent flow, grants the requested scopes, and we receive an access token plus a refresh token. The refresh token lives in the operator's secret store (or DB), per-user.

In this pattern, **x1agent.com publishes one OAuth Client per provider** as part of the platform build. Customer installs use that shared Client through the standard consent screen — exactly how Linear, Notion, Figma, and other SaaS tools handle Google Drive. The customer doesn't need a Cloud Console project of their own.

This is the right pattern for **Google Drive / Workspace, Notion, Calendar, Linear**, and most user-scoped third parties that don't have a manifest flow. See ticket X1A-82.

### 3. Dynamic Client Registration (RFC 7591)

When the provider supports [RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591), our api can register an OAuth client programmatically — no manifest UI, no user pre-registration. Some MCP servers support this; x1agent's [Zone-3 MCP](/architecture/overview) plumbing already uses it via the curated-registry picker.

This is the right pattern for **MCP servers** that publish a metadata endpoint with `registration_endpoint`.

### 4. Marketplace listing

When the integration is meant to be broadly distributed and domain-administered (Slack App Directory, Google Workspace Marketplace), we list the App once and customers' admins install it from the marketplace. This is mostly orthogonal to the other patterns — the App itself can still be created via manifest flow (#1), but the install path is one-click from the customer's admin console.

This is the right pattern for **Slack** and for **Google Workspace domain-wide** delegation. Most installs don't need this; per-user OAuth (#2) is usually enough.

## What never happens

- Operators do not paste private keys into config files.
- Customer-side admins do not register OAuth Clients in their Cloud Console.
- x1agent.com servers never see another tenant's GitHub App credentials, Google client secret, or webhook secret. Credentials flow provider → operator's own api → operator's own secret store.

## The narrow exception: install-time bootstrap secrets

A small set of values legitimately have no third-party to register with — they're operator-controlled and exist purely to bootstrap the install:

- `JWT_SECRET` — signing key for platform session tokens. Auto-generated by the installer; not customer-facing.
- `API_INTERNAL_TOKEN` — shared secret between the api and sidecar. Auto-generated.
- `WORKSPACE_SECRETS_MASTER_KEY` — KEK for envelope-encrypting workspace secrets. Auto-generated.

These are populated by `mise run configure:prod` (or hand-edited in `installs/<base-domain>.local`) and live in the operator's secret store from then on. The dynamic-flow rule does not apply because there's no provider on the other end to register against.

## What this means for `mise run configure:prod`

The configure wizard captures the small set of install-time values that *must* exist before the cluster comes up — cloud target, base domain, admin emails, the bootstrap secrets above, and the LLM credential (Anthropic key or Vertex region). Everything else is wired through the admin UI **after** the install is running, using one of the four flows above.

So for a fresh install you should:

1. Run `mise run configure:prod` once. Answer the required questions. Skip everything optional.
2. Run `mise run install:prod`. Cluster comes up; api/app reachable on your base domain.
3. Sign in as a platform admin. From the admin UI, register the GitHub App, connect Google Drive, attach MCP servers — all via in-product buttons, all without copy-paste.

The configure wizard still accepts pasted credentials for the optional integrations as a fallback for cases where the operator already has a manually-registered App (e.g. they're migrating from another install). The fallback is **not the recommended path**. New installs should leave those blank during configure and use the in-product flows after the cluster is up.

## Spotting a violation

If a feature ships and the only way to wire it in is "paste this six-line PEM block into a config file," that's a defect, not a feature. File a ticket to replace it with one of the four flows. Customers running their own x1agent install should never need to assemble a private key by hand.
